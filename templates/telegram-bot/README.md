# Telegram Bot Template (OpenClaw-wired)

A Telegram managed bot that routes inbound messages to an [OpenClaw skill](../openclaw-skill). This is the distribution shape we use at 2BFT — Telegram is the user surface, OpenClaw is the runtime.

## What it does

- `/start` — onboarding message
- `/help` — lists supported commands
- Any other text message → forwarded to the `summarize_text` OpenClaw skill, reply posted back

## Quickstart

```bash
# 1. Get a bot token from @BotFather and put it in .env
cp .env.example .env

# 2. Install Node deps
npm install

# 3. Make sure the OpenClaw skill side is set up
cd ../openclaw-skill && python -m venv .venv && \
  source .venv/bin/activate && pip install -r requirements.txt && cd -

# 4. Run
npm start
```

Message your bot. Send any text and you'll get a 3-bullet summary back, generated by the OpenClaw skill running in a subprocess.

## How the OpenClaw wiring works

`src/openclaw.js` spawns `python -m cli` inside the sibling `openclaw-skill/` directory, pipes the payload as JSON on stdin, and reads the result back on stdout. It's deliberately the smallest possible adapter — no HTTP, no message bus — so you can see the contract clearly before scaling it up.

For production, swap the subprocess call for an HTTP request to your OpenClaw runtime:

```js
// instead of: callSkillSubprocess('summarize_text', payload)
await fetch(`${OPENCLAW_URL}/skills/summarize_text`, {
  method: 'POST',
  body: JSON.stringify(payload),
});
```

## Ops notes

- Long-poll mode (default) is fine in dev. For prod, switch to webhooks via `bot.launch({ webhook: { ... } })`.
- Telegraf catches handler errors but doesn't retry — wire your own retry/queue if the skill side can be flaky.
- The skill subprocess pays ~100ms startup overhead per invocation. Fine for low volume; for high volume, run OpenClaw as a long-lived service and hit it over HTTP.
